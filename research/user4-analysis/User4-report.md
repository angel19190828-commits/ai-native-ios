## 核心发现

### 发现 1：用户建立了“冗余提醒系统”，不是一个提醒

User 4 不只创建日历事件。她查看路线、预留准备时间、设置提前提醒，并为了保险增加起床保障。

**设计含义：**AI 不应只提供“加入日历”，而应生成一个由事件、通勤和准备提醒组成的计划，同时避免重复或互相矛盾的通知。

### 发现 2：邮件仍然是被动的长期记忆库

用户明确选择不在当前设置中保存地点，因为当天可以返回邮件查看。这减少了当下录入，但把未来的检索成本留给了自己。

**设计含义：**不要强迫用户复制所有信息；系统可以保留可追溯的邮件来源，并在日历、路线和提醒中安全引用同一地址。

### 发现 3：路线规划受地区与地图可靠性影响

User 4 因当前地区的地图数据情况选择 Google Maps，而不是默认接受一个地图来源。

**设计含义：**AI 不能把路线时间伪装成确定事实。应显示地图来源、交通方式、估算时间与更新时间，并允许用户切换来源。

### 发现 4：没有明显操作困惑，但存在系统组织成本

她完成任务流畅，没有表现出显著犹豫或不会操作。痛点不在单个 App 的可用性，而在于她必须自己理解各工具之间的依赖并创建多重保障。

**设计含义：**本项目不需要重新设计 Calendar 或 Maps 的基本操作；机会在跨应用任务组织、上下文连接与提醒去重。

### 发现 5：准备事项的完整性仍不透明

口述重点覆盖时间、路线和提醒，但没有观察到明确处理“携带作品集”等准备要求。无法据此断言她忘记了，但当前完成状态也无法证明所有邮件要求都已转化。

**设计含义：**最终确认应使用来源完整性清单，明确显示每一项邮件要求是已处理、忽略还是待确认。

## 与前三位用户的关系

- 与 User 2 一致：路线与通勤时间是日历之外的必要步骤。
- 与 User 2 / User 3 一致：邮件继续作为核对来源，系统没有统一任务记忆。
- 与 User 3 不同：User 4 没有强调手动录入的记忆价值，更强调多层提醒与保险。
- 为当前设计增加新要求：不仅要连接 App，还要识别并减少重复提醒，同时公开地图来源和路线估算依据。

## 对当前设计的影响

### 保留

- 邮件触发的轻量建议与来源透明。
- Calendar → Maps → Reminders 的后台任务轨道。
- 通勤计算过程和建议出发时间。
- 最终执行前确认、逐项修改和撤销。

### 新增或加强

- 地图卡片显示路线来源、交通方式和更新时间。
- 允许用户选择或确认出发地，不默认猜测“家”。
- 检测日历提醒与闹钟是否重复，并提出合并建议。
- 最终计划增加“来源完整性清单”，尤其检查地点、提前到达和携带材料。
- 完成后仍保留一键返回原邮件，而不是复制后切断来源。

## 研究限制

- 当前为单位参与者的探索性观察，不能代表总体比例。
- 自动转写存在专有名词误识别，报告仅使用上下文明确的内容。
- 由于录屏分辨率与界面细节限制，提醒是在 Calendar 内还是独立 Reminders 中完成，需要在访谈回问后才能完全确认。
- “未观察到处理作品集”不等于用户一定忘记，只说明现有流程缺少可验证的完整性状态。
